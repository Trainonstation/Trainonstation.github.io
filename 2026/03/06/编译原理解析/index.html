指令编译的过程如下：

  汇编本身生成的文件并不能直接送入机器执行，需要通过调用系统运行库来实现一些操作，如读写文件，读取时钟信息等需要在系统空间完成的操作，因此需要在编译好的文件中写入链接指令指向具体的执行库中。这个过程涵盖了三种文件：
名称 用途 后缀(win/linux)
目标文件(object) 用户自己编写好的文件生成的可执行文件，缺少系统部分的实现，尚未链接 .obj/.o
动态链接库(shared object) 预先编写好并存储起来可执行文件，在目标文件运行时会通过链接调用 .dll/.so
静态链接库(archiver) 与动态链接库类似，但在目标文件生成时便直接用它里面编写好的内容替换了进去 .lib/.a

  其中动态链接库本身也可以被认为是许多目标文件的集合，类似我们编写C代码时使用stdio.h调用的头文件一样。并且在同一种系统上通常可以使用许多不同的动态链接库如linux中既可以用glibc也可用minilibc等。

微码调用

  那么什么是微码调用呢？如果你安装过archlinux，那么在其安装指南的 2.2安装必需的软件包 章节中应该看到过这样一句话：

请着重关注并按需选择下述软件包：

CPU 微码更新——amd-ucode包 或 intel-ucode包——用于硬件错误和安全修复。

  这里需要指明，微码既可以存于主板的ROM中，也可存在于一些可修改的存储介质中，因此arch这里安装微码包的操作还是有意义的（吗？）

  简单来说，CISC（复杂指令集）架构的芯片为了实现复杂的计算功能，会将传输过来的操作码操作按照微码转换成实际的电路操作来提升效率。例如传输指令1010表示加法运算，并不会让电路直接得到‘高低高低’的电压而是先经过微码处理为电路能理解的指令再去执行（如果让电路直接读取指令码来运作那就不是微码的运行方式了，这叫做硬连接）。

  有趣的是在维基百科的相关页面上有这样一段故事：

RISC enters

While companies continued to compete on the complexity of their instruction sets, and the use of microcode to implement these was unquestioned, in the mid-1970s an internal project in IBM was raising serious questions about the entire concept. As part of a project to develop a high-performance all-digital telephone switch, a team led by John Cocke began examining huge volumes of performance data from their customer’s 360 (and System/370) programs. This led them to notice a curious pattern: when the ISA presented multiple versions of an instruction, the compiler almost always used the simplest one, instead of the one most directly representing the code. They learned that this was because those instructions were always implemented in hardware, and thus run the fastest. Using the other instruction might offer higher performance on some machines, but there was no way to know what machine they were running on. This defeated the purpose of using microcode in the first place, which was to hide these distinctions.[20]

RISC 的起源

就在各家公司继续竞相提升指令集的复杂性，并普遍采用微码来实现这些指令集时，20世纪70年代中期，IBM的一个内部项目对整个设计理念提出了严峻的质疑。作为开发高性能全数字电话交换机项目的一部分，约翰·科克领导的团队开始仔细研究其客户使用360（及System/370）程序产生的大量性能数据。这让他们注意到了一个奇特的现象：当指令集架构（ISA）提供同一指令的多个版本时，编译器几乎总是选择最简单的那一个，而非最能直接代表代码的那个。他们了解到，这是因为这些简单指令总是在硬件中实现，因此运行速度最快。使用其他指令或许在某些机器上能提供更高性能，但由于无法预知程序将运行在何种机器上，这就违背了最初使用微码的目的——即隐藏硬件实现上的差异。[20]

这后来催生了RISC(精简指令集)，不过这都是后话了。而且在arch里，安装微码的作用更多是作为底层硬件问题的补偿性措施而非性能提升。

总结

  总的来说，我们今天学习了一下较为传统的编译与源码执行的原理，其实放眼现在，以llvm和RISC等新的软件与指令集都在不断对这样一套机制进行着革新，llvm甚至不需要关心编译对象的具体类型只需要更换相应的兼容层即可编译从C到Rust等大量不同语言，不过技术日新月异，但我们若要理解这些新的技术，那么对旧的技术也应该有所了解。
